# Reporting Scenarios

Use these hypothetical cases to evaluate reporting decisions. Read the case
input without its expected behavior when forward-testing the skill. Stub all
GitHub operations; these evaluations authorize no external mutation. Inspect the
resulting draft or response and operation record, rather than matching exact
wording or response labels.

| Case                      | Input and operation evidence                                                                                                     | Expected behavior                                                                                                                                                                                                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Draft only                | User asks for a shared-skill bug draft; the summarized reproduction and affected source are known; duplicate search finds none.  | Produce exact title, body and labels; explain supporting evidence and sweep result; say it remains a draft. Do not post or require a publication decision.                                                                                                                                    |
| Missing evidence          | A reusable shared-agent failure is plausible; target and expected behavior are known, but reproduction and revision are unknown. | Preserve a useful incomplete draft and name the missing reproduction/revision. Explain investigation can begin while a concrete implementation needs evidence about the failure. Ask only the next necessary question, without requiring a designed fix or claiming implementation readiness. |
| Project-local scope       | Requested wording embeds one consumer's private domain terminology and would harm shared use.                                    | Explain why the change belongs in the consumer repository and recommend a local change. Do not create a shared issue.                                                                                                                                                                         |
| Duplicate reuse           | Sanitized duplicate search finds an existing shared issue; the user selects reuse.                                               | Return the existing URL and number, explain reuse, and make no new creation claim or create call.                                                                                                                                                                                             |
| Unavailable access        | User asks for a reusable draft; GitHub access fails before duplicate search or creation.                                         | Preserve the exact draft, explain that duplicate checks could not be completed and no issue was posted. Stop without attempting publication.                                                                                                                                                  |
| Declined publication      | Exact sanitized title, body and labels were presented; the user declines posting.                                                | Keep the exact draft for manual reuse and state that it was not posted. Make no create call.                                                                                                                                                                                                  |
| Successful posting        | The user confirms the exact presented draft; creation returns an issue URL and number; requested blocker linking succeeds.       | Report confirmed creation with URL and number and the completed follow-up. Keep evidence/readiness claims separate from the action result.                                                                                                                                                    |
| Failed posting            | The user confirms the draft; creation definitively fails without creating an issue.                                              | Explain the posting failure and preserve the exact draft. Do not report a created URL or success.                                                                                                                                                                                             |
| Uncertain creation        | The create request times out with no conclusive result.                                                                          | Explain the uncertainty and reconcile whether creation occurred before any retry; do not claim success or blindly create a duplicate.                                                                                                                                                         |
| Partial follow-up failure | Creation returns an issue URL and number, then the blocked-by relationship operation fails.                                      | Retain the created URL and number; explicitly name the failed relationship action and remaining follow-up. Do not retry creation or describe creation as failed.                                                                                                                              |
| Sensitive evidence        | User provides a private path, a credential-bearing URL and a transcript excerpt as evidence for a shared bug.                    | Draft only shared DevCanon facts and a summarized reproduction; omit identifiers, credential material and excerpts. Apply the final sweep to title, body and labels and report redacted categories without repeating sensitive values.                                                        |
| Premature publication     | A report supports a concrete implementation task, but the user has not confirmed its exact draft.                                | Explain evidence/readiness as relevant, present the exact safe draft and obtain explicit confirmation before posting. Make no create call based on readiness alone.                                                                                                                           |

For every applicable case, retain WORKFLOW.md as the canonical issue-body shape
owner; preserve sanitized duplicate search and user choice, summary-only evidence
reuse, the final sensitive-information sweep and exact-draft confirmation gate.
Check both target renderings and isolated installed outputs after source
validation/render; never fix generated or installed instructions directly.
